# Phase Planning Workflow

## When to Use

当一个阶段性里程碑完成后，用户说"下一步做什么"时使用。具体触发条件：
- 完整的路线图（W1-W6）已执行完毕
- 用户想继续推进但没指明具体方向
- 需要基于项目实际状态 + 行业趋势做决策

## 五步流程

### Step 1: 代码库扫描（了解现状）

并行派发两个子任务：

**子任务 A: 代码度量**
```
目标: 获取项目关键数据
- 总代码行数、文件数（按类型分类）
- 测试数量、通过/失败统计
- Git 状态（未提交变更、上次提交时间）
- 关键文件大小（巨型文件的识别）
- 代码味道检测（超长函数、重复结构）
```

**子任务 B: 模块健康度**
```
目标: 评估每个模块的健康状态
- tools/: 强壮度、单函数长度
- gateway/: 平台适配器一致性
- cli/hermes_cli/: 模块化程度
- run_agent/: 测试覆盖率
- 未跟踪的新文件（说明正在进行的开发）
```

### Step 2: 行业趋势研究（了解外部）

研究当前行业趋势（5 个方向）：
1. **多 Agent 编排** — Obra/Superpowers ★184k, LangGraph ★31k, CrewAI ★51k
2. **上下文管理** — 各家主流方案的上下文策略
3. **MCP 生态** — FastMCP ★25k, MCP servers ★85k
4. **自改进/评估** — Reflexion 模式、A/B 评估
5. **新生产工具** — 12-Factor Agents ★19k, Mastra ★23k

关键：**用 GitHub API + 直接抓取**（搜索引擎可能被 CAPTCHA 拦截）

### Step 3: 能力差距分析

将 Step 1（现状）和 Step 2（趋势）对比，找出 2-3 个明确方向。
每个方向要回答：
- 用户当前有什么？
- 行业最佳实践是什么？
- 差距在哪？
- 填补差距后带来什么**可感知的效果**？

### Step 4: 用户价值解释（关键）

**不能用技术术语解释抽象概念。**
必须用"现状 vs 升级后"对比法，让用户直观理解：

```
现状（当前能力）:
  你: "帮我做三件事"
  delegate_task(tasks=[A, B, C]) → 返回三个碎片，手动拼

升级后（新能力）:
  你: "帮我做一份完整报告"
  DAG(A → [B, C] 并行 → 自动合并) → 出成品
```

**解释核心**：用户关心的不是"实现了什么技术"，
而是"我之前做这件事要交互 5 轮，现在 1 条指令搞定"。

### Step 5: 产出可执行计划

使用 writing-plans skill 产出 W+数字 的周计划，包含：
- 每周围绕哪个方向
- 具体操作步骤（精确到文件路径）
- 验证命令（能跑的命令行）
- 每个任务的价值点
- 风险和注意事项

## 输出格式

计划保存到 `.hermes/plans/YYYY-MM-DD_HHMMSS-phase-name.md`

包含：
```
## 执行策略
### W7 — 方向 A 任务名
**目标**: 一句话
**操作步骤**: 1. 2. 3.
**变更文件**: 列表
**验证**: bash 命令

### W8 — 方向 B 任务名
...
```

## 关键经验教训

1. **先扫描再研究** — 知道现状才能知道差距，否则研究方向会太泛
2. **不要同时搞 5 个方向** — 选 2-3 个最有价值的，用户选择
3. **用户价值比技术细节重要** — 解释"效果"而不是"原理"
4. **DAG 的解释要用"流水线类比"** — 用户最容易理解的概念：原料→加工→组装→成品
5. **每次 Phase 结束都要重新扫描** — 代码库在变化，旧数据不可靠
6. **委托子任务做扫描和研究** — 并行执行节省时间，同时可以比我自己搜索更深入

## 配合使用的 skill

- writing-plans — 产出可执行计划
- search-generate-separation — 搜索结果需要用文件中转
- subagent-driven-development — 计划中的具体实现可委托执行
