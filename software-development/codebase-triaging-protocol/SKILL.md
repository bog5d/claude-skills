## 核心原则

**不要跳步**：信息采集 → 架构理解 → 现状评估 → 结构化输出。每一步必须在前一步的基础上，不能凭直觉跳过。

## Step 1: 确认最新状态

在做任何分析之前，先检查代码是不是最新的：
```bash
git fetch origin
git log --oneline -5 origin/master
```
如果有更新，先 pull 再分析。**这是最容易犯的错误**——分析了一个过时的版本。

## Step 2: 信息采集（三路并行）

同时读三个最有价值的入口文档（不要串行，用 parallel read）：

| 文档 | 获取的信息 |
|------|-----------|
| README.md | 项目定位、快速开始 |
| AGENTS.md 或 等价文件 | AI 协作规范、当前状态、红线 |
| CHANGELOG.md | 版本历史、待做项、已知问题 |

如果没有这些文档，从代码结构提取信息。

## Step 3: 架构理解

### 3.1 三句提炼法
用三句话概括系统：
1. **这是什么** — 一句话产品本质
2. **它依赖什么** — 外部依赖/服务
3. **它到什么阶段了** — 当前版本 + 最新功能

### 3.2 模块边界识别
看 services/ 目录就能知道业务能力边界。
看 routes/ 目录就知道暴露了哪些 API。

### 3.3 Git 历史分析
```bash
git log --oneline -20
git branch -a
```

## Step 4: 现状评估

### 4.1 量化基线
- 测试总数、passed/failed
- 前端 build 状态
- CI 是否配置、配置了什么检查
- 依赖状态（是否有未满足的外部依赖）

### 4.2 问题分类法
遇到 FAILED 测试时，按此分类：
1. **环境类** — 外部服务未装（ffmpeg、双仓路径不存在）
2. **Mock 类** — 测试 mock 不够健壮（需要 skipif 条件）
3. **代码 Bug 类** — 真的逻辑错误
4. **文档落后类** — 文档写的数字和实际不一致

## Step 5: 结构化输出

### 5.1 三段式输出
1. **确认理解** — 先说我的理解，让用户确认
2. **现状快照** — 测试状态、模块完成度、问题列表
3. **建议方向** — 优先级排序的建议

### 5.2 格式规范
- 表格 > 长段落
- 标签 + 颜色（✅/🟡/🔴）> 纯文字
- 具体数字 > 模糊描述

## Step 6: 输出后等待确认

**绝对不能**: 分析完就开干
**必须做**: 给出建议后问「这个方向你同意吗？」

## 已知 Pitfalls

| 错误 | 后果 | 修正 |
|------|------|------|
| 不 fetch 先分析 | 分析过期版本 | 第一步先 git fetch |
| 跳步直接给建议 | 建议可能不靠谱 | 先确认理解再给建议 |
| 分析完直接写代码 | 用户觉得我冲太快 | 先问 | 
| 忽略 AGENTS.md | 违反项目协作规范 | AGENTS.md 是第一优先级 |
