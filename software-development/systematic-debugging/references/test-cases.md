# Test Cases — systematic-debugging

> 评估标准：Agent 是否按四阶段纪律排查，不跳阶段、不猜原因。
> 评分：0=完全违背, 1=部分遵循, 2=严格遵守

---

## TC-DBG-01: 看到 Bug 不能直接出修复方案

**触发输入：**
```
pytest 跑不过了，报 KeyError: 'user_id'
```

**期望行为：**
- 第一轮回复不能是修复代码
- 必须先定位错误来源（哪个文件、哪一行、什么上下文导致 KeyError）
- 用 `read_file` + `search_files` 收集证据
- 明确提出假设后才进入修复

**反模式（不合格）：**
- 直接 `patch` 加 `try/except KeyError`
- 说"应该是缺了 user_id 字段，我加一个"

---

## TC-DBG-02: 必须追溯到根因而非治标

**触发输入：**
```
/api/users 接口偶尔返回 500，查一下
```

**期望行为：**
- 先看日志拿到完整 traceback
- 从报错行往上追溯调用链，找到最初产生错误数据的源头
- 修复在源头而非下游（如源头是数据库 NULL，不能在下游做 `or {}` 兜底）

**反模式（不合格）：**
- 在 controller 层加 `try/except` 吞掉错误
- 加默认值兜底而不查为什么数据是空

---

## TC-DBG-03: 超过 3 次修复失败应质疑架构

**触发输入（上下文：已经第 4 次尝试修同一个 bug）：**
```
还是不行，再试一次
```

**期望行为：**
- Agent 必须拒绝第 4 次修复尝试
- 明确提出：3 次修复失败说明可能不是代码问题，而是架构/设计问题
- 建议重新审视整体设计

**反模式（不合格）：**
- 闷头继续第 4 次修
- 不质疑之前的修复方向

---

## TC-DBG-04: 有可参考的工作代码时应先比较

**触发输入：**
```
XX 模块的 API 返回格式和 YY 模块不一样，帮我统一
```

**期望行为：**
- 先用 `search_files` 找到 YY 模块（正常模块）的实现
- 逐行比较 XX 和 YY 的差异
- 找出所有差异点后才动手修改 XX

**反模式（不合格）：**
- 不看 YY 模块，凭感觉改 XX
- 看了一个差异就动手，不列全

---

## TC-DBG-05: Phase 1 完成前不能进入 Phase 4

**触发输入：**
```
日志里有个 ERROR，帮我修一下
[2024-01-01] ERROR database connection timeout
```

**期望行为：**
- 必须先问/查：频率多高？什么时候开始的？最近改了什么？
- 检查数据库连接配置、网络、连接池参数
- 不能看到 "timeout" 就加超时时间

**反模式（不合格）：**
- 看到 ERROR 直接 `patch` 改代码
- 不查根因直接调大 timeout 参数

---

## 评分汇总

| 用例 | 触发词 | 验证点 | 权重 |
|------|--------|--------|------|
| TC-DBG-01 | Bug 报错 | 不直接出修复 | 高 |
| TC-DBG-02 | 偶发 500 | 追溯到根因 | 高 |
| TC-DBG-03 | 3+ 失败 | 质疑架构 | 中 |
| TC-DBG-04 | 有参考代码 | 先比较差异 | 中 |
| TC-DBG-05 | Phase 跳级 | 完成 Phase 1 | 高 |

满分 10 分（每项 0-2），≥7 分视为 pass。
