## 核心沟通原则

### 1. 先理解，后行动
波总希望你**先充分理解背景再动**。他的典型模式：
- 让你「理解一下某个系统」→ 你需要读代码、读文档、读 git log
- 然后让你「讲你的看法」→ 输出结构化的分析
- 然后问「下一步怎么做」→ 再出计划
- 最后才说「开干」

**教训**：我第一次被问 FOS 后，直接跳到了「下一步行动清单」，虽然分析得不错，但他后面又让我拉取最新代码再重新审视——说明我漏了第一步：先看看远程有没有更新。

### 2. 信息同步优先于执行
波总非常重视「别人 pull 仓库就知道发生了什么」：
- CHANGELOG 必须更新
- 文档必须同步
- commit message 要规范
- 他亲自在 GitHub 上维护了一个协作规范层（PR template、AGENTS.md、ci.yml）

所以任何时候我做了决策/分析/代码变更，**第一优先级是让它可被同步**，不是「做完就好」。

### 3. 先沉淀，再继续
当他突然说「先沉淀反思」——这是信号：
- 他觉得我冲太快了
- 他希望我把学到的变成长久的知识（skill），而不是留在 session 上下文里
- 他在训练我「做项目不是只写代码，更要积累方法论」

### 4. 硬核沟通风格
- 不喜欢废话套话
- 喜欢结构化输出（表格、分类、标签）
- 对「模糊描述」零容忍
- 会直接纠正我的失误（「先拉取最新再说」）

### 5. 重复失败的铁律

当同一个任务尝试 3 次以上仍未成功（如 gateway 反复启动不了、bot 反复不响应）：
- **停止盲试** → 系统诊断根因（读日志、读源码、对比正常case）
- **一次性拉全貌** → 不要逐步排查，一次 terminal 调用拉所有相关数据
- **如果自己修不好** → 诚实告知 + 列出已知根因 + 建议下一步，不要隐瞒

## 期望清单

| 维度 | 期望 | 示例 |
|------|------|------|
| 分析深度 | 读代码，不只是读 README | git log + 代码结构 + 测试状态 |
| 输出结构 | 表格/分点/标签 | 能力矩阵、优先级分类 |
| 同步纪律 | 每次变更必须可追踪 | 更新 CHANGELOG + commit + push |
| 节奏控制 | 出计划后先问，不自己冲 | 「这个优先级你同意吗？」 |
| 知识留存 | 学到的东西变成 skill | session 结束前沉淀 |

## 触发词

| 波总的说法 | 真实的含义 |
|-----------|-----------|
| 「先理解一下」 | 先读代码读文档，不要输出 |
| 「你觉得呢」 | 出结构化的分析 |
| 「下一步怎么弄」 | 出行动清单 |
| 「先沉淀反思」 | 停止执行，把经验变成 skill |
| 「开干」 | 可以开始编码了 |
| 「先不要着急」 | 我方向偏了，先停下 |
| 「存成长期记忆」「以后换AI来也能用」 | 把凭证/架构知识存入 mem0 + memory + skill，确保跨 AI 会话可接盘 |
| 「把这些记进去」 | 大量凭证一次性吐出，需要全部保存到持久层（mem0 为主，memory 为索引） |
| 「你就全面分析一下，你能不能把它修好」 | **不要再反复试错了**——已经重启 N 次没修好。需要系统诊断根因后再动手，不是继续盲试 |
| 「你这份是新的还是旧的」 | **质疑交付质量**——不要用模糊词（"报告完好"），必须给出精确证据：时间戳、数据来源、技能框架版本 |

## 凭证记忆铁律

当波总一次性发送大量账号密码时：

1. **全部存入 mem0**（每条一个独立事实，便于语义检索）
2. **Memory 存紧凑索引**（仅存关键标识符 + 一条"所有外部凭证在 mem0"的指针）
3. **对外操作时绝不日志明文**：curl/terminal 命令中用 mem0_search 调取密钥，不在 stderr/stdout 中暴露
4. **凭证有了就用，不要重复问**：如果 mem0 已有对应服务凭证，直接使用，不需要让用户再发
