# Tool Risk Matrix

## 核心原则

- 优先专用工具，不优先终端万金油
- 优先只读工具，不优先写入工具
- 优先小样本验证，不优先全量操作
- 优先可回滚路径，不优先不可逆路径

## 工具选择顺序

### 文件相关

1. 看文件内容：`read_file`
2. 找文件/搜内容：`search_files`
3. 小范围改动：`patch`
4. 新建或整文件重写：`write_file`
5. 复杂工程改动：`aider_edit`
6. 只有上面都不合适时再考虑 `terminal`

### 代码与流程相关

1. 单一工具调用：直接调工具
2. 3+ 步且有分支/循环：`execute_code`
3. 大幅工程改动：`aider_edit`
4. 推理重、可隔离的子任务：`delegate_task`

### 搜索与页面相关

1. 查网页事实：`web_search`
2. 动态交互页面：browser 工具链
3. 先看 schema / skill，再决定要不要浏览器自动化

## 风险分级

### 低风险

- `/tools` / `/tools/{name}`
- `read_file`
- `search_files`
- `web_search`
- `skill_view`
- `skills_list`
- 只读浏览

策略：直接做。

### 中风险

- `patch`
- `write_file`
- `execute_code`
- `terminal` 的只读命令
- `memory`
- `todo`

策略：先读现状，先小样本，做完后校验。

### 高风险

- 会改系统状态的 `terminal`
- 批量 patch / 批量 write
- `send_message`
- `cronjob`
- 委派后自动执行改动
- 任何副作用未知的私有工具

策略：先确认目标、先小范围验证、必要时先问用户。

## 典型 if-then 规则

- **如果** 用户说“看看怎么回事” → **先** 读 / 搜 / 抽样，不写。
- **如果** 用户说“帮我改一下” → **先** 读原文件，再 patch，小改优先，不直接覆盖。
- **如果** 用户说“批量处理” → **先** 拿 1-3 个样本验证。
- **如果** 工具第一次用 → **先** 看 schema，再最小输入测试。
- **如果** 连续两次同类错误 → **换方法**，不要死磕。
- **如果** 要通知别人 → **先** 确认目标与内容，再发送。

## 失败切换路线

1. 猜参数失败 → 查 `/tools/{name}`
2. 终端方式脆弱 → 换专用工具
3. 多步手工太长 → 换 `execute_code`
4. 小 patch 不稳 → 换 `aider_edit`
5. 全量风险太大 → 退回样本验证

## 高风险前的十秒确认

- 我已经读过现状了吗？
- 我知道影响范围吗？
- 我有验证样本吗？
- 我知道失败后怎么恢复吗？
- 现在执行比继续确认更合适吗？
